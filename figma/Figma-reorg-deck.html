01 · Recommendations

What Figma itself advises

The main point from Figma's official guide: there is no single standard — there are a few base models that teams mix and match to fit their product.

  • Keep files small and nimble. One file for the whole system eventually "explodes" — split by feature/section.
  • Separate "done & in prod" from "in progress." The source of truth must not mix with experiments.
  • One Design System as a separate library. A dedicated team/project so it's clear where the source of truth lives.
  • Descriptive naming + named versions. Instead of Auth_v3_final2_copy — a named version with a date in history.
  • A governance ritual. Agree who moves work between states and when (a "quality day").
Source: Figma — Team, project & file organization and the Best Practices hub. Links on the last slide.

How the tech giants see it

🇺🇸 Uber · Base

Start with 3 files

"Most teams cram everything into one file until it explodes. We recommend starting with 3 separate files." A shared navigation template across all teams.

base.uber.com
🇸🇪 Spotify · Encore

Visible & discoverable to all

Open-sourced their Figma playbook. Their #1 structure criterion is "visible and discoverable by everyone." A project lead per component.

Modular file split

Fully public structure. The UI Kit = separate files: Tokens, Component library, Icons — each publishing its own library.

design.gitlab.com
🍎 Apple · HIG

Shared foundation, device on top

Devices aren't isolated silos: a shared foundation of decisions (tokens/components) + adaptation per device.

02 · Variants

First — Figma's base nesting

Every model below is just a different way of laying work out inside this hierarchy.

02 · Variant A

One file, split into pages

This is where we started. Every section is a page in a single file. Simple at first, but the file gets heavy and everyone edits the same space.

➕ Simple start, everything nearby.   ➖ Gets heavy, edit conflicts, "where's the current version?" — this is exactly the wall we already hit.
02 · Variant B

Main file + tasks that merge back

A separate file (or branch) per task. When it's done, it merges back into the main file. This is exactly the model you described.

➕ Clean main file, each task isolated, easy to tie to a ticket.   ➖ Without branching and strict naming you get lost in versions — the same headache you had at Universe Group.
02 · Variant C

By state: Production / Feature / Archive

Projects split by "maturity." It's transparent what's live and what isn't yet. Figma's officially recommended model for teams that care about state visibility.

This is the base of our recommendation — closest to what you intuitively described.
02 · Variant D

By process stage: a pipeline

Files are physically dragged between stage-projects as they mature. Handy for teams with clear review sessions (often agencies).

➕ Maximum status transparency for stakeholders.   ➖ Lots of manual dragging; overkill for small teams.
02 · Variants E + F

Modular Design System  ·  Branching

E · Modular DS (Uber / GitLab)

Separate library files are published into all feature files. One source of truth for the system.

F · Branching (git-style)

A branch off main per ticket. While the designer works, dev keeps looking at a stable main. Done → merge.

It's not either/or. Mature teams combine: e.g. C (state) + E (modular DS) + F (branching). That's exactly what we build for Inito.
03 · Conclusion

There's no single standard — and that's fine

The right structure is the one the team is comfortable with and can actually follow every day.

  • Each product is its own organism. Take the principles, don't copy someone's structure 1:1.
  • For Inito we take a hybrid: C (by state) + a shared foundation (Apple/GitLab) + rituals + optional branching.
  • It's not about folders, it's about governance. Without sync rules, any structure goes stale.

Choice criteria

Not "how cool it looks," but:
1) is it easy to find the current version,
2) is it clear what's in prod,
3) will the team actually stick to it.

03 · Conclusion

Recommended structure for Inito

Key addition: inside a file — sub-pages per flow (Onboarding, Zoom, Settings…). On a flow page we split into sections: "✅ In production" and "🚧 In development." When "in development" reaches prod → move it to the "In production" section + a named version with the date.
04 · The problem

What causes the mess in Inito

The root pain isn't the folder structure — it's the gap between design and prod in time and communication.

1

Time lag. Designs go into development 1–2 months later. The context is lost by then.

2

Changes without us. Dev changes text, spacing, or reworks a screen — and no one tells design.

3

Figma isn't updated. The mockup stays in its old state and "sits there" as a false source.

4

No single source of truth. Old and new are mixed → it's unclear what's actually in prod.

5

No process owner. No one is formally responsible for syncing → drift keeps accumulating.

05 · Solution

How it's solved

✓

One Source of Truth. The Production file = only the real state of prod, separated from experiments.

✓

Branching instead of copies. A branch per task; main stays stable for dev.

✓

Statuses + "in prod / in dev" sections. Visible right in the file what's ready and what isn't (like Headway).

✓

Named versions with dates. "2026-06 — Onboarding v2 shipped" instead of final2.

✓

A contract with dev. Changed a screen in prod → file a "update Figma" ticket. Without it, drift returns.

✓

A governance owner + a per-sprint ritual. Someone runs the "prod ↔ Figma" sync regularly.

05 · Solution

Step-by-step rollout plan

1

Week 1 — Skeleton. Create the projects: Design System · Production · In Progress · Playground · Research · Archive. A file template with "in prod / in dev" sections.

2

Week 1–2 — Audit. Reconcile every screen with the real prod. Current → Production, drafts → Playground, dead → Archive.

3

Week 2 — Rules. Lock in naming, named versions, the contract with dev. One agreement doc for the team.

4

Ongoing — Ritual. Once per sprint: sync prod ↔ Figma. Assign a governance owner.

Validate first: whether all devices live in separate files vs a shared foundation; whether dev will accept the "changed → ticket" contract; projects vs pages for splitting states (depends on permission needs).
